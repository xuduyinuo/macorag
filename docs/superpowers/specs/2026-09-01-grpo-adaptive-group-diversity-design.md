# GRPO Adaptive Group Diversity Design

## Goal

Reduce uninformative `group_size=4` rollout groups without permanently doubling the cost of every training sample. Preserve the existing role-round credit objective, generate extra candidates only when the initial group produces no trainable advantage, and use a conservative terminal-advantage fallback for singleton role-round buckets.

The first implementation targets the observed run in which 527 of 1000 samples were skipped as `zero_advantage`. The acceptance target is a zero-advantage skip rate below 25% on a fixed 100-sample smoke run, without increasing protocol failures or changing the main task reward formula.

## Scope

This design changes the repository-native GRPO rollout collection, action-advantage assignment, configuration, checkpoint compatibility, and training diagnostics. It does not change the initializing SFT adapter, retrieval backend, prompt contract, base `group_size: 4`, query/evidence/answer reward components, or evaluation metric implementation.

The first version deliberately does not add a novelty bonus, alter retrieval cost, rebalance role reward weights, select only the highest-reward candidates, or permanently set `group_size: 8`. Those changes would modify the optimized task and belong in separate reward ablations if adaptive expansion remains insufficient.

## Observed Diversity Boundary

The current 1000-sample run already uses distinct per-prompt generation seeds. Across initial groups of four, query paths average 2.566 unique values and are all identical for only 23.2% of samples. Diversity collapses downstream: final answers average 1.397 unique values, terminal rewards are all identical for 71.1% of samples, and aggregate rollout rewards are all identical for 53.7%.

Therefore the first intervention must not treat seed propagation as broken. It must spend extra sampling only after the task rewards prove that the original four candidates are uninformative.

## Configuration Contract

The canonical GRPO configuration retains `group_size: 4` and adds:

```yaml
adaptive_group_expansion: true
max_group_size: 8
group_expansion_step: 4
max_group_expansion_attempts: 1
diversity_retry_temperature: 1.0
singleton_terminal_fallback_weight: 0.2
```

`group_size` is the initial candidate count. `max_group_size` is the hard per-sample candidate limit, and `group_expansion_step` is the number generated by one retry. `max_group_size` and `group_expansion_step` must be positive integers, `max_group_expansion_attempts` must be a non-negative integer, retry temperature must be finite and strictly positive, and fallback weight must lie in `[0, 1]`. When adaptive expansion is enabled, the maximum must be larger than the initial group and at least one expansion attempt must be allowed.

All six fields are training-semantic checkpoint fields. A full-state resume rejects changes to them because they alter rollout sampling, generation-counter consumption, advantages, optimizer history, and subsequent sample behavior.

When adaptive expansion is disabled, the effective behavior is identical to the existing fixed-size path. When the fallback weight is zero, singleton buckets retain their current zero-advantage behavior.

## Adaptive Expansion Algorithm

For each training sample, the trainer first generates the configured four candidates using the existing batched rollout path, per-prompt seeds, retrieval environment, and policy trace recording. It computes action rewards, terminal rewards, role-round decision returns, and advantages exactly as it does now.

A group is uninformative when every trainable action has absolute advantage at or below the existing zero-advantage tolerance. This is intentionally the same condition that would otherwise produce `skipped_update_reason: zero_advantage`; expansion does not introduce a competing definition of trainability.

If the initial group is informative, training continues immediately with four candidates. If it is uninformative and expansion is enabled, the trainer generates another batch of up to `group_expansion_step` independent candidates without resetting the policy generation counter. Retry generation uses `diversity_retry_temperature`, while all other decoding, prompt, retrieval, and maximum-round settings remain unchanged.

The trainer appends every retry candidate to the original group. It does not cherry-pick candidates by reward or discard the original four. Rewards and advantages are then recomputed jointly over the full effective group so every candidate participates in the same comparison population. If the expanded group is still uninformative, the existing zero-advantage skip remains the final behavior.

Expansion repeats only while all of the following hold:

- the group remains uninformative;
- `max_group_expansion_attempts` is not exhausted;
- the effective group is smaller than `max_group_size`.

The default configuration permits exactly one expansion from four to eight. With the observed 53.7% reward-tie rate, the expected candidate count is approximately 6.15 per sample, about 54% more rollout work rather than the 100% increase caused by a permanent group size of eight.

## Sampling and State Safety

The policy generation counter remains the sole seed cursor. Every prompt generated during an expansion consumes a new counter value, is persisted in complete checkpoints, and is restored on resume. An interrupted run can therefore reproduce the same future seed sequence only from the latest complete checkpoint, consistent with the existing atomic-resume contract.

Retry temperature applies only to retry candidates for the current sample. The policy's normal temperature must be restored in a `finally`-safe scope before processing another sample, including generation, parsing, retrieval, or reward exceptions. A cleaner implementation may pass a sampling override through `generate_batch`; it must not mutate shared process-wide configuration without guaranteed restoration.

All expanded candidates use independent RAG state, trace, retrieval history, and parse-error state. Batched retrieval may share cache entries but cannot share mutable candidate state.

## Singleton Role-Round Fallback

The primary advantage remains the normalized decision return within each `(role, round_index)` bucket. Buckets with at least two members continue to use the existing role-round formula without blending in rollout-level feedback.

A bucket with exactly one member has no same-state peer and currently receives zero advantage. For that singleton only, the trainer computes a group-wide normalized terminal advantage over all effective rollouts and assigns:

```text
singleton_action_advantage = singleton_terminal_fallback_weight
                             * normalized_terminal_advantage(rollout)
```

The fallback uses `compute_action_rewards().terminal_reward`, not the legacy aggregate `reward_total`, so it does not reintroduce the known supporting-fact capping mismatch. A singleton still receives zero when the group terminal rewards are identical.

The default weight `0.2` limits the influence of this weaker counterfactual comparison. The fallback exists to retain limited credit for later-round actions that occur in only one variable-length trajectory; it is not used to manufacture preferences between otherwise tied full rollout groups.

Adaptive expansion evaluates informativeness after singleton fallback. Diagnostics must separately report primary role-round signal and fallback-only signal so a nominal optimizer update cannot hide a group whose useful evidence came from only one singleton action.

## Data Flow and Interfaces

Rollout collection is separated into three explicit operations:

1. generate a requested number of independent candidate rollouts;
2. compute rewards and assign primary plus singleton-fallback advantages over the complete candidate set;
3. decide whether to expand, train, or preserve the existing zero-advantage skip.

The reward/credit operation must be safe to call again after appending candidates. It replaces previously derived advantage and credit fields rather than accumulating them. Retrieval and generation timing from all attempts are accumulated once in the final sample metrics.

The serialized rollout-sample record stores all effective candidates and preserves their generation order. Existing best-rollout reporting remains diagnostic only and does not affect which candidates train the policy.

## Diagnostics

Each training JSONL row adds:

```json
{
  "initial_group_size": 4,
  "effective_group_size": 8,
  "group_expansion_attempts": 1,
  "group_expansion_triggered": true,
  "reward_unique_count_before": 1,
  "reward_unique_count_after": 3,
  "terminal_unique_count_before": 1,
  "terminal_unique_count_after": 2,
  "primary_nonzero_action_fraction": 0.54,
  "fallback_nonzero_action_fraction": 0.03,
  "final_nonzero_action_fraction": 0.57
}
```

Run metadata records the expansion and fallback configuration. Checkpoint manifests include the same semantic fields. Aggregate analysis must be able to report expansion rate, expansion success rate, average effective group size, zero-advantage rate before and after expansion, unique reward counts, role-specific nonzero-advantage rates, parse-failure rate, and additional rollout time.

An expansion is successful only when primary role-round signal becomes nonzero. Fallback-only nonzero actions are reported separately and do not count as expansion success.

## Failure Handling

Generation, parsing, retrieval, and reward exceptions follow the existing fail-safe behavior and retain diagnostic partial traces where supported. Retry-temperature overrides are restored before propagating an exception. Expansion cannot exceed the configured candidate or attempt limits.

If retry candidates parse incorrectly, they remain part of the effective group and receive the existing parse penalties; the trainer does not silently replace failed candidates until a favorable group appears. This prevents adaptive sampling from becoming outcome-based rejection sampling.

Non-finite rewards, terminal scores, or assigned advantages fail before backward. A group that remains finite but uninformative is skipped exactly as before. Optimizer, scheduler, vLLM synchronization, and checkpoint step semantics remain based on successful optimizer updates and consumed samples under the existing contract.

## Verification Strategy

Unit tests cover configuration validation, disabled-mode compatibility, no expansion for informative initial groups, one expansion for tied groups, hard maximum enforcement, retry-temperature propagation and restoration, monotonic generation-counter consumption, and recomputation over all original plus retry candidates.

Advantage tests cover unchanged multi-member role-round normalization, singleton fallback from action terminal reward, zero fallback for tied terminal rewards, fallback weight zero, variable-length trajectories, finite-value validation, and proof that legacy aggregate reward is not consumed.

Logging and checkpoint tests cover all new per-step diagnostics, metadata fields, critical fingerprint fields, full-state resume compatibility, generation-counter restoration after expanded groups, and serialization of all effective candidates.

A deterministic fake-policy integration test constructs an initial four-way reward tie and an informative retry batch. It verifies one optimizer update, participation of all eight candidates, no reward-based candidate selection, and a single scheduler/vLLM synchronization step.

After CPU tests pass, a real 100-sample smoke run uses the same selected qids and order as the current experiment. It passes the diversity gate only when:

- final `zero_advantage` skip rate is below 25%;
- optimizer update rate is above 70%;
- mean unique aggregate reward count is at least 2.3;
- Query, Evidence, and Answer each retain measurable primary nonzero advantages;
- parse-failure and missing-answer-tag rates remain below 1%;
- mean effective group size and runtime overhead are reported;
- gradients remain finite.

Passing the smoke gate permits a fixed SFT/checkpoint-300/checkpoint-1000 evaluation under the existing evaluation contract. It does not by itself prove final-answer improvement. If adaptive expansion fails the gate, a separate design will consider task-aligned dense process rewards rather than silently adding novelty bonuses to this implementation.
